支付逻辑漏洞和 SQL 注入、RCE 不一样，它不是代码执行，而是业务规则没校验清楚，其实就是客户端传来的金额、数量、状态、优惠信息都不可信

## 支付流程节点

选商品数量 → 选支付/配送方式 → 生成订单号 → 选订单支付 → 完成支付

可测参数：商品ID、购买数量、购买价格、订单属性、折扣属性、支付方式、支付状态等

## 数量篡改

后端信前端传的数量就出事。测试值：

```
qty=-1
qty=0.1
qty=999999
```
不在前端能不能改，在后端有没有重算订单金额

## 价格篡改

请求里带 `price=5400` 且后端直接用，改：

```
price=-1
price=0.01
price=999999999999
```

整型溢出：int 范围 `-2147483648~2147483647`，超过最大值可能溢出成负数或异常  金额必须后端按商品ID+数量+活动重算，不能客户端传

## 订单对冲

先建两个订单 A（便宜）B（贵），替换参数用 A 价买 B：

```
替换商品ID / 订单ID / 支付订单号 / 支付成功回调参数
```
支付成功状态没和原始订单、商品、金额强绑定

## 支付状态绕过

系统只判断"支付成功"状态，不查支付的是哪个订单、金额对不对、流水真不真、订单和商品ID对不对  回调参数能替换就绕过  只信回调状态，不校验流水和金额

## 优惠券复用/盗用

`use_coupon=2`，后端只看参数不校验完整状态：

```
重复用同一张 / 枚举用别人的 / 关闭订单后券返还但旧订单仍可支付
```
券是不是当前用户的、用过没、过期没、适用商品/活动、是否已绑订单

## 积分对冲/算法溢出

余额-10、积分+10，把 amount 改成 `-10`，后端简单减法就反向计算，余额/积分反增

是否正数、是否整数、是否超上限、余额够不够、积分够不够、兑换方向合法、前后总额一致

## 怎么挖

找关键数据包 → 分析金额/数量/订单/券/积分参数 → 不按正常流程走 → PC/APP/小程序多端都试

重点接口：下单、订单确认、支付发起、支付回调、券领取、券核销、积分兑换、订单关闭、退款、签到/活动

## 修复

后端重算订单金额；数量必须正整数+限最大值；支付金额必须和第三方实际一致；优惠券校验用户/状态/范围/次数；订单状态严格流转；支付状态和真实流水强绑定；退款原路原单；关键参数加签；金额异常进人工审核

## 核心

客户端传来的任何金额、数量、状态、优惠信息都不可信。扫描器可关注请求里的 price/amount/money/total/qty/count/num/coupon/use_coupon/integral/balance/pay_status/order_id/trade_no/openid/user_id 字段
