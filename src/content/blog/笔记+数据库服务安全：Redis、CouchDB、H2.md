核心逻辑：数据库/中间件/大数据组件一旦暴露 + 认证或权限出问题，就能从访问服务升级到读数据、越权、写文件、命令执行

## 通用判断流程

```
发现服务 → 判断端口/指纹 → 判断是否认证 → 判断版本/CVE → 判断权限 → 评估危害
```

看到 6379 不一定是 Redis 漏洞，看到 5984 不一定是 CouchDB 漏洞。要判断：服务是否可访问、是否需要认证、版本有无 CVE、当前权限能做到什么

## Redis（端口 6379）

存 Session/Token/验证码/缓存/用户信息/配置。没认证就能直接连、读业务数据

例：
- CVE-2022-0543：Lua 沙箱绕过 RCE
- CNVD-2019-21763：模块加载 RCE
- CNVD-2015-07557：未授权写文件（webshell/crontab/SSH authorized_keys）

写文件利用条件苛刻：进程权限高、目录可写、知道 Web/系统目录、protected-mode 关闭、服务暴露

防护：不暴露公网、绑内网、强密码、开 protected-mode、限安全组、禁用/重命名危险命令、低权限跑

## CouchDB（端口 5984）

NoSQL，HTTP API，访问端口常返回 JSON 指纹

例：
- CVE-2017-12635：垂直越权/创建管理员
- CVE-2017-12636：命令执行

检测：5984 是否开放、根路径是否返回 CouchDB JSON、`/_utils` 管理界面是否可访问、是否允许匿名建用户/访问库、版本是否在影响范围

防护：不暴露公网、开认证、限 `/_utils` 和管理 API 来源、关匿名写入、升级

HTTP API 型数据库默认暴露，风险比传统数据库更直观，很多操作直接走接口

## H2 Database（端口 8082 Web Console / 9092 TCP）

Java 生态轻量数据库，常用于开发/测试/嵌入式。不该出现在公网或生产

例：
- Web Console 暴露 + 未授权访问
- CVE-2022-23221：JDBC URL/INIT 参数 RCE

Console 暴露且无严格认证，能构造 JDBC URL 加载外部 SQL 脚本触发命令执行

检测：有无 Console 页面、能否无认证进入、是否允许远程 JDBC、版本是否低于修复、能否加载远程脚本

防护：生产关 Console、限本地访问、升级、禁远程 JDBC、开发调试组件不暴露公网

## 核心

服务层漏洞判断模型：暴露没 要认证不 认证能绕不 版本有 CVE 不 当前权限能读数据/写文件/执行命令不 能影响业务或主机不

Redis 代表缓存未授权+写文件，CouchDB 代表 HTTP API 型越权，H2 代表开发组件暴露 RCE
